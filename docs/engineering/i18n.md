# Internationalisation (en, ta, kn)

The UI ships in English, Tamil and Kannada. Locales, formatters and message catalogs live in
`packages/i18n` (`@causedeck/i18n`); `apps/web` wires them into next-intl. Court content and
uploaded documents are never translated or transliterated: content language is tagged with
`ContentLang` instead (see the formatters in `packages/i18n/src/format`).

## Layout

```
packages/i18n/
  src/messages/<locale>/<namespace>.json   source catalogs (edit these)
  src/generated/messages/<locale>.json     merged catalog per locale (generated, committed)
  src/generated/messages.d.ts              `Messages` type from en (generated, committed)
  translation-status.json                  draft | reviewed per ta/kn key
  glossary.json                            legal terms and approved ta/kn renderings
  scripts/{gen-types,check-catalogs,extract}.ts
```

Namespaces are `common`, `nav`, `shell`, `auth`, `workspace`, `members`, `notifications`,
`settings` and `errors`. Each file holds whole top-level keys, and a locale's catalog is the
merge of its files. Call sites therefore use the top-level key, not the file name:

| File                 | Top-level keys                    |
| -------------------- | --------------------------------- |
| `common.json`        | `common`, `theme`, `home`         |
| `nav.json`           | `nav`, `palette`, `shortcuts`     |
| `shell.json`         | `shell`                           |
| `auth.json`          | `auth`                            |
| `workspace.json`     | `workspace`                       |
| `errors.json`        | `error`, `notFound`, `offline`    |
| `members.json`       | `invite`                          |
| `notifications.json` | (none yet: notifications screens) |
| `settings.json`      | (none yet: settings screens)      |

A top-level key may live in one file only; `pnpm i18n:check` fails otherwise.

The next-intl plugin (`apps/web/next.config.ts`) precompiles the generated per-locale files, which
keeps the ICU parser out of the client bundle. `apps/web/i18n/request.ts` loads only the active
locale through `@causedeck/i18n/server`, so only that locale's messages reach the client.
`pnpm --filter @causedeck/web bundle:budget` fails if a ta/kn string turns up in the en home route.

## Adding or changing a key

1. Add the key to the same file in `src/messages/en`, `ta` and `kn`. Keys are stable dotted ids;
   messages use ICU MessageFormat (`{name}`, `{count, plural, one {# hearing} other {# hearings}}`).
2. Add the key to `translation-status.json` under `ta` and `kn` as `draft`.
3. Run `pnpm i18n:types` to regenerate the merged catalogs and the `Messages` type.
4. Run `pnpm i18n:check`.

`t()` keys are typed: `apps/web/global.d.ts` points next-intl's `AppConfig` at `Messages`, so an
unknown key fails `typecheck`.

`pnpm i18n:check` (also a CI step in the `test` job) fails on:

- a key missing from, or extra to, ta/kn compared with en;
- an empty string;
- invalid ICU syntax;
- ICU arguments or rich-text tags that differ from en;
- a ta/kn string identical to en, unless allow-listed (`CauseDeck`, `name@example.com`, or a key
  in `allowUntranslated`);
- stale generated files;
- a `translation-status.json` that misses a key, names an unknown key or uses a value other than
  `draft`/`reviewed`.

`pnpm --filter @causedeck/i18n i18n:extract` lists literal `t('…')` keys used in `apps/web` that
the en catalog lacks.

## Missing keys at runtime

- **Development**: the UI shows the dotted key (`nav.today`) and logs a warning.
- **Production**: the server fills any ta/kn gap with English while loading the catalog and
  reports the keys to the logger (`i18n: messages missing, rendering English`). Anything still
  missing renders as its key and is reported. The UI never shows an empty string.

The handlers come from `createMissingKeyHandlers` in `@causedeck/i18n` and are installed on the
server (`getRequestConfig`) and on the client (`components/intl-provider.tsx`).

## Translation workflow

Machine-assisted first drafts are acceptable to unblock building screens, but every ta/kn key stays
`draft` in `translation-status.json` until a native speaker reviews it. `pnpm i18n:check --report`
prints the draft/reviewed counts per locale and namespace, the glossary terms awaiting review, and
strings that use a glossary term without its approved rendering.

Copy tone is plain, respectful and professional. Legal terms use the court-accepted vernacular
where one exists; otherwise keep the English term in Latin script with a gloss (for example
`Cause list`).

## Indic rendering

Tamil and Kannada rules live in `packages/ui/tokens/typography.css` (the `:lang(ta)` / `:lang(kn)`
block) and the font setup in `apps/web/app/fonts.ts`:

- **Line-height >= 1.7 on body text.** The lang rule adds `--leading-indic-delta` (0.15) to body and
  prose leading and raises the size-paired `--text-*--line-height` tokens that Tailwind `text-*`
  utilities read, so every body step (xs to lg) stays at 1.7 or more. Headings, labels and emphasis
  use the tighter `1.25 + delta`.
- **No letter-spacing, no uppercase, weight 400-500.** Tracking is reset to `--tracking-normal`,
  `text-transform` to `none`, and headings and emphasis cap at `--weight-medium`.
- **Per-script sizing.** The Noto Sans Tamil and Kannada faces carry `size-adjust: 96%`, which puts
  their letter body on the Geist x-height. It is on the faces, not `font-size-adjust`, so Latin text
  keeps its size.
- **Latin tabular numerals.** Geist comes first in the font stack, so digits in dates, case numbers
  and INR render in Latin with `tabular-nums` (`packages/ui/tokens/base.css`).
- **Wrap, don't truncate.** Long ta/kn labels wrap: `Button` drops `whitespace-nowrap` and its fixed
  height (the size's height becomes a minimum) under `:lang(ta)`/`:lang(kn)`. Shell controls with a
  fixed width give Tamil/Kannada labels room (topbar search) or a smaller step (phone tab bar).

`e2e/tests/i18n/indic-rendering.spec.ts` checks this in ta and kn at 360/768/1280, light and dark,
on a specimen (conjuncts, glossary terms, every body size, a long button label and numerals), the
sign-in page and the shell. It reads computed styles and layout, and Chromium's platform-font report,
which shows every Tamil/Kannada string shaped by the shipped Noto face with no system-font fallback or
tofu. It runs without baselines:

```sh
pnpm --filter @causedeck/e2e test tests/i18n/indic-rendering.spec.ts --project=chromium-360-light
```

The spec's `@visual` screenshots (`specimen-<locale>.png`, `sign-in-<locale>.png`,
`shell-<locale>.png`) skip until baselines exist. Generate them with the e2e workflow's
`update_snapshots` dispatch in the pinned Playwright image (`e2e/README.md`), never locally. The
members page joins the spec once it exists (#25).
